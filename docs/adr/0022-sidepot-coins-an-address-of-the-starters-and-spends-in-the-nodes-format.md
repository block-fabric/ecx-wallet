# Sidepot coins: an address of the Starter's own, and spends in the node's format

Besides its game accounts (ADR 0021), the Sidepot sidechain has ordinary coins: outputs held by 20-byte addresses, as on Thunder, the LayerTwo Labs chain its node is a fork of. A game cashout arrives as one, and only a coin can ask for a withdrawal to the main chain. The wallet had no address there, so a player had nowhere of their own to cash out to and no way back to eCash. Now `sidepot.wasm` has one, and builds and signs the two spends a player needs. The wallet follows no chain for it (a light client): Sidepot's server lists the address's coins and takes its transactions.

- **The address** is one key's, with nothing derived below it and no change address. Its seed is the BIP32 private key at `m/300'/88'/1'` of the Slot's Starter (its BIP39 seed, no passphrase): the game account's path with account 1 for 0, the same on every network. Sidepot signs with Schnorr over ristretto255, so that 32-byte secp256k1 key is only a seed: BLAKE3 in key-derivation mode, context `ECX Wallet 2026-11-20 Sidepot coin key v1`, takes it to 64 bytes, which are reduced onto ristretto255's scalar field. The result is a signing key as the node's `frost_ristretto255` reads one, a nonzero scalar in its canonical 32 bytes. The address is the first 20 bytes of BLAKE3's XOF over the compressed verifying key, written in plain base58 with no version and no checksum, as the node writes it. `declare()` lists `coins`.
- **The node's formats, reimplemented.** `core/sidepot/src/thunder.rs` is the node's `thunder_types` byte for byte: outpoints, outputs, coins (`PointedOutput`), transactions and authorizations in their canonical (Borsh) bytes and in the JSON the node's RPC reads and writes. A transaction's txid is the BLAKE3 of its canonical bytes, without its Utreexo proof. An input is an outpoint and the BLAKE3 of the coin it spends. Each input is authorized by the verifying key of its coin's address and that key's signature of the transaction's canonical bytes: `R | z`, with the challenge `SHA-512("FROST-RISTRETTO255-SHA512-v1" | "chal" | R | key | message)` reduced onto the scalar field (RFC 9591's ciphersuite, signing alone). The module uses the node's curve crate (`curve25519-dalek` 5.0.0, without its tables) and `blake3`, and neither `thunder_types` nor `frost-ristretto255`: they draw randomness to sign and bring a node's dependencies.
- **No randomness.** A module imports nothing, so the nonce is derived: BLAKE3 keyed by a key derived from the signing key (context `ECX Wallet 2026-11-20 Sidepot coin signature nonce v1`), over the message, 64 bytes reduced onto the scalar field. One message gets one nonce and one signature, as in Ed25519. Every signature is verified before it leaves the module.
- **Two spends**, built by `build_coin_spend` from the coins the server lists: a **transfer** of an amount to another Sidepot address, and a **withdrawal request** (the node's `Withdrawal` output: a payout, a main-chain fee and a main-chain address, held at the wallet's own address until the chain bundles it). It spends only the address's own plain coins, the largest first, and returns what is left to the same address. The fee is the inputs less the outputs. The chain sets no minimum: the wallet pays a flat 1,000 sats (`SIDEPOT_COIN_FEE`).
- **A withdrawal's main-chain address** is read with the parent's encoding from the Chain Entry (`params.parentAddressParams`, a copy of the root's, as Elements' entry has): P2PKH, P2SH, P2WPKH, P2WSH and P2TR, as the main chain's own Send pays. The node takes any network's address and signs only its script, so the module refuses another network's, and writes the address back in its canonical text. The payout must be above Bitcoin Core's dust threshold for its script (294 sats to P2WPKH, 546 to P2PKH): one output below it would make the whole bundle a transaction the main chain doesn't relay. The main-chain fee must be above zero.
- **Built means Clear.** The unsigned spend is `{ transaction, coins }`: the transaction and the coins it spends. `decode_coin_spend` checks it from those bytes alone: every input names its coin by hash, every coin is a plain coin of the Starter's address, none twice, a withdrawal pays an address of this network from the wallet's own address, and the inputs cover the outputs. Its answer is a Clear View in the shape every module's has: a withdrawal request is a `withdrawal` destination with the `withdrawalBurn` dangerous mode, as Elements' is. `sign_coin_spend` makes the same checks before it signs. The wallet refuses, as its own bug, a view that isn't exactly the payment asked for, at most one output of change to itself, and the flat fee (`isSpendAskedFor`).
- **Not Signing Requests.** `check`, `decode`, `sign` and `finalize` still refuse on Slot 88, and the Provider has nothing new: a site can't hand the wallet a Sidepot transaction to sign. The spends come only from the wallet's own screens.
- **A server that lies can't spend.** A coin's value reaches the signature through the coin's hash in its input, so a server that misstates a coin gets a transaction the node refuses. One that hides coins shows a lower balance. The balance itself is reported, not verified, and the screen says so.
- **A cashout says whose address it pays.** The entry's view (ADR 0021) now carries `destAddress` (the destination in base58) and `destYours`, which `sidepot.wasm` works out from the same Starter. The approval shows "Yours" for the wallet's own address, and otherwise warns that nothing in a Sidepot address catches a typo.

## The `sidepot` Server API, for coins

Beside `/state` and `/account/<key>` (ADR 0021):

- `GET /coins/<base58 address>`: `{ height, coins }`, the address's coins as the node's `list_utxos` lists them. A coin's content is `{ "Value": sats }` or `{ "Withdrawal": { value, main_fee, main_address } }`, a request waiting to be bundled. The wallet refuses a list with a coin of another address.
- `POST /tx`: the node's `Authorized<Transaction>` as JSON, with an empty proof (`{ "targets": [], "hashes": [] }`) for the node to fill. `{ txid }`, or HTTP 400 with the node's own words, which the wallet shows. The wallet checks the txid against its own.
- `GET /withdrawal-bundle`: the chain's pending withdrawal bundle, or `null`. Its `spend_utxos` are the requests it pays.

- **Balance:** the sum of the listed plain coins, less those a spend of the wallet's own holds.
- **Held coins** (`sidepot-coins-held:<chain>` in `host.persistent`): the outpoints a spend took, until the server lists none of them any more (the spend is in a block) or 6 Sidepot blocks have passed (`HOLD_BLOCKS`; it never got there).
- **One spend at a time**, in the Slot's place in the spend queue; the web wallet takes a lock of its own for it (`ecx-wallet:spend:coins:<slot>`).

## Withdrawals waiting, and where the server stops

A withdrawal request is a coin of the address (`waiting`) until the chain's pending bundle includes it (`bundled`). When that bundle reaches the main chain, the node removes its requests from its coins and the bundle is no longer pending: through the months the main chain's miners then vote on it, neither `/coins` nor `/withdrawal-bundle` lists the request, and nothing says whether it was paid. If the bundle fails, the node puts the requests back as coins (`connect_withdrawal_bundle_failed` in the node's `two_way_peg_data.rs`, read 2026-11-20).

So the wallet keeps the requests it made itself (`sidepot-coins-withdrawals:<chain>` in `host.persistent`: the request's outpoint, its amounts and address, the chain's height then, and whether the server has listed it since). One the server listed and no longer does shows as `handedOver`, saying that its bundle has gone to the main chain and that the wallet can't follow it from there; one never listed after 6 blocks shows as `unlisted`. Each of those two has "Stop showing it", which forgets only the wallet's record. A wallet restored elsewhere has no such record, and shows only what the server lists.

## What the user sees

On Sidepot's screen, under its game balance: **Coins on Sidepot**, with the balance, Receive (the address, with Copy and a QR code), Send and Withdraw (`#/coins/<slot>/send`, `#/coins/<slot>/withdraw`, each approved in place like Send and Deposit), and **Withdrawals waiting**, each with where it stands. The Withdraw form says plainly that a withdrawal is slow and depends on the main chain's miners.

## Checked against the node

`core/sidepot/thunder-vectors` is a small program built against the node's own `thunder_types` (not part of the wallet's build). It wrote `core/sidepot/tests/fixtures/thunder-vectors.json`: keys with their verifying keys and addresses, coins and transactions with their canonical bytes, hashes and txids, the node's own signatures, and transactions signed as the node's wallet signs them. `core/sidepot/tests/coins.rs` holds the module to each of them. The other way, the same program read eight transactions the module signed (transfers, and a withdrawal request to each kind of main-chain address), with the node's types, and checked them with the node's `verify_authorized_transaction`: its answer is `fixtures/wallet-signed.json`. The module signs without randomness, so the test checks it still makes those transactions byte for byte.

Checked on 2026-11-20 on a private test chain (an eCash regtest with Slot 88 active, and a Sidepot node and server for it), by hand-run scripts that aren't part of the test suite, with a build of this wallet for that chain that isn't part of this repository. In node, with the wallet's own code (`createSidepotCoins`) and that build's modules: a game cashout of 2,000,000 sats (the node's `game_cashout`) was listed at the address the module derived; a transfer of 500,000 sats was taken by `POST /tx` (`9f77b545…dd9034f8`) and listed at the recipient's address a block later, with the change at the sender's; a withdrawal request of 300,000 sats with a 1,000 sat main-chain fee was taken (`7238fd6d…1e89ff48`), listed as a `Withdrawal` coin and in `/withdrawal-bundle`, and later paid on the regtest main chain (`b8ae7a96…acc8cabe`, block 15,044); and the node refused a signed transaction with one amount changed ("failed to verify authorization"). In headless Chromium, with that chain's web build: two wallets made on the Create screens, each address read from Receive, a cashout to the first, Send approved in place (`d96f53a5…15261a2b`) and shown in the second wallet's screen, and Withdraw approved in place (`c522f082…86577145`), shown under Withdrawals waiting as sent and then as in the next bundle. The statuses a withdrawal request goes through after that (`handedOver`, back to `waiting` when its bundle fails, `unlisted`), the release of held coins, and a refusal by the server were walked through in node against a made-up server, not in a browser.

A third spend, a move of coins into the wallet's own game account, came later: ADR 0023.

## Considered options

- **Depend on `thunder_types`, or on `frost-ristretto255`:** rejected. The first is a node's crate (LMDB types, `rustreexo`, `utoipa`, `rayon`); the second signs with a random nonce from a generator the module doesn't have. A module here imports nothing (core/README.md).
- **Randomness from the host for the nonce:** not now, as for entries (ADR 0021). A derived nonce is as valid, and can't repeat for two messages.
- **The key at `m/300'/88'/0'`, the game account's, used for both:** rejected. One secret would sign under two schemes on two curves, BIP340 and this one.
- **The secp256k1 key's bytes reduced directly onto ristretto255's field:** rejected. Hashing with a context of its own keeps the two keys unrelated, and the 64-byte reduction leaves no bias.
- **The spends as Signing Requests** (`check`, `decode`, `sign` on Slot 88, format `sidepot-entry`): rejected for now. It would let a site ask for a signature on a Sidepot transaction it built, which nothing needs yet.
- **The coins as part of the chain's balance**, added to the game account's in `accounts.reported`: rejected. The game spends only the account, and a Send spends only the coins: one number would be right for neither.
- **A new address for change:** not now. It needs a scan for used addresses, which the server's API has no way to do but one address at a time.
- **Checking the server's coins against the chain** (Utreexo proofs, headers): out of scope. The wallet reads every chain from its server, unverified (ADR 0002).

## Consequences

- Home's total doesn't count Sidepot coins: it adds each chain's reported ECX, which on Sidepot is the game balance. They show only on Sidepot's screen.
- Sidepot's Activity doesn't list coin transfers: the server's API has no history of an address. A spend shows its txid once, when sent.
- A coin sent to the address while a spend of the wallet's is unconfirmed is spendable at once; the spend's own change only once it is in a block.
- A Sidepot address has no checksum. The wallet can't catch a mistyped one, and says so on the Send form and in a cashout's approval.
- A withdrawal request can't be taken back. If its bundle fails, the chain bundles it again.
- The wallet can't say when a withdrawal is paid, or that its bundle is being voted on: Sidepot's API reports neither. An API that listed a bundle's status by address would let it.
- The same screens ship in the mainnet build, whose Sidepot server is BlockFab's explorer (`https://explorer.blockfab.org/sidepot/api/v1/l2/feature/game`). It must answer the routes above (`/coins/<address>`, `POST /tx`, `/withdrawal-bundle`; `/coin-history/<address>` and `/withdrawal-notice` if it has them) for the coins to show. Everything here was checked on the test chain only.
- `getAddresses({ slot: 88 })` still answers only the game account. A site that needs the wallet's Sidepot address asks the user for it.
